## 宿題

### 取り組んだレベルと実装

**実装**。`app/retrieval.py`に`expand_neighbors(hits, pages)`を追加し、ベクトル検索の返却処理に組み込んだ。

1. 元の検索ヒットを元の順位どおり先頭に残す。
2. 各ヒットについて、同じ`document_id`のPDFページ番号−1と＋1を検索する。
3. 存在するページの全文・タイトル・章・資料ID・ページ番号を付加する。欠番は飛び越えない。
4. `(document_id, page)`で重複を除く。追加ページをさらに展開しない。最大5×3=15ページ。
5. 元ヒットは`retrieval_role=seed`、追加ページは`neighbor`とし、`neighbor_of`でどのヒットから加わったかを残す。追加ページに検索距離を流用しない。
6. `AIE_RAG_NEIGHBORS=1`で有効にする。既定の0は従来検索。指示文、ツール名・説明文、top-kは変更していない。Graphの入口は明示的に通常検索を使用する。

### 比較の設計

`compare_rag_neighbors.py`で質問・期待するふるまい・必要なページを先に定義した。

| ID | 質問の狙い | 固定検索語と、先に確認した根拠 |
|---|---|---|
| single | LoRA/QLoRAの基本説明 | `LoRA QLoRA 違い` → 第2回p.52 |
| memory | コンパクションとセッションをまたぐメモリ、日々のメモ | `コンパクション セッションをまたぐメモリ 日々のメモ 長期メモリ` → 第3回p.13,39,40 |
| absent | 今回作ったRAGの実測平均応答時間・正答率 | `今回作ったRAG 実測平均応答時間 正答率` → 資料には実測ログがなく、確認できないと答える |
| adjacent | LoRA/QLoRAと、直後のチャットボットのページにあるAPI形式指定の優先順位・FTが効く振る舞い | `LoRA QLoRA 違い` → 第2回p.52,53 |

宿題の比較は検索語を固定した**検索→1回生成**のRAGである。エージェントが検索語を変える演習のループとは区別する。各組で通常検索の上位5ページが同一であることを実測結果で確認し、モデル・温度・質問・回答指示・資料・DBをそろえた。変えたのは前後ページを付加する取得処理だけ。

adjacentは、短い検索語が複合質問の後半を拾えない状況を意図的に作った、調整用の例である。自然な全質問を使う検索や、エージェントによる追加検索より優れていると主張する実験ではない。後半の検索語を別に投げる方法も次の比較候補になる。

実行順はsingle/absentがbaseline→neighbors、memory/adjacentがneighbors→baseline。各条件1回。失敗した429試行は残したが、比較表には成功した試行だけを採用した。最後の組はレート制限の時間を置いて再実行したため、時刻やAPIの混み方は完全には固定できていない。

### 役立った例：p.53の根拠を追加取得できた

adjacentの通常検索はp.52,51,60,47,61で、必要なp.53がなかった。前後ページを加えるとp.53を取得でき、必要な根拠2ページの被覆は1/2→2/2になった。回答もp.53を引用し、「口調」「根拠の付け方」という振る舞いの例を出せた。

ただし**取得の改善が、完全な回答の改善になったわけではない**。p.53には「形だけ守らせるならAPIの構造化出力が先」とあるが、改良後の回答は「何を使うことが先とされているでしょうか」とヒントに留まり、優先順位を明答しなかった。通常版はそもそもp.53を読まず、p.60–61を「直後」の説明のように扱っており、質問の後半を十分に支えられていなかった。

### 不要な情報が増えた例

singleはp.51–52で答えられた。前後追加で5→11ページ、入力2,511→4,934トークンとなったが、回答の本質的な追加はない。p.48の継続事前学習やp.62の次回予告などは、この質問の固定・学習・量子化の説明には不要だった。根拠の必要数1ページに対し、取得候補が増えた分を有用な改善と数えない。

absentは5→15ページ、入力2,526→6,688トークンへ増えたが、どちらも実測値は確認できないと答えた。資料自体にないログは隣接ページを広げても得られない。回答は資料中の例の正答率を今回の実測値として流用しなかった。

### 残る失敗

memoryは通常検索ですでにp.13,39,40が取得できた。前後追加版も必要なページを保持したが、日々のメモが全部長期メモリになるかの説明を、図を見て考えるヒントに寄せた。通常版は「全部は移さない」「基準を超えたものだけ」と具体的に説明した。本文に根拠があるのに十分に答えない、生成段階の不足が残る。

宿題の完成解答を避ける指示は、一般的な理解質問への明答まで控えさせることがある。今回は取得処理だけを比較するため指示は変更していない。次の実験では通常の理解質問と完成解答の要求を区別する指示を、別の変更として検証したい。

### CLI統合の確認

通常の`app.agent`のCLIでも`AIE_RAG_NEIGHBORS=1`を読み込ませ、`--trace`付きでsingleを実行した。1回の`search_materials`からseed5＋neighbor6=11ページを取得し、最終回答はp.51–52を根拠に説明した。3.47秒、入力5,451/出力167トークン、モデル応答2回、生成推定$0.002053。これは統合確認であり、固定検索語の上記比較とは別測定である。

この端末の既定httpx2通信が前回タイムアウトしたため、実測ランナーはSDKの公開`http_client`引数でhttpxを指定した。pydantic-ai 2.57.0では対応しているが、v3で削除予定の非推奨経路。CLI確認時も同じproviderへ差し替えた。モデル・資料・指示の変更ではない。

### テスト・記録

- 現在のブランチの自動テスト24件成功。APIを使わない配線テストと、前後取得の境界・重複・欠番・順位保持・入力を破壊しないこと・設定の切替を確認した。
- 配布DBとJSONの214件の本文・資料IDを照合した。
- `verification/exercise.json`：演習4方式の回答・ツール呼び出し・使用量。
- `verification/homework.json`：4組8条件の回答・取得ページ全文・ID・時間・使用量。429失敗試行も別行として保持。
- `verification/cli_neighbors.txt` / `cli_neighbors_calls.json`：通常CLIのtraceと11ページの取得記録。
- ここでいう評価はCodexが本文を読んで確かめた観察。人による独立評価、反復実験、統計的に有意な精度向上の主張ではない。

### 採用したい方式と気づき

既定は通常検索のままにし、前後の説明が重要な質問で必要に応じて追加取得する形が、この用途には妥当だと考える。今回の実装はオン/オフの比較用で、必要性を自動判断するところまでは実装していない。取得根拠が増える利点はあるが、全質問でトークンを増やすことや回答を長くすること自体は目標ではない。

1回ずつの結果から時間の優劣は判断しない。モデルの出力・長さ・サーバーのキャッシュや混雑でも変わる。次は、質問種別ごとの複数回測定と、引用箇所が回答を支えるかの独立した確認を追加したい。
